## Why the card kept answering about the page {#relevance}

You wrote that context is what makes the information useful, and that we
should work on that part. The two relevance reports are the same defect, and
naming it precisely is what makes the rest of the list tractable.

A biased search asks Wikipedia for **the selection and the page's topic
together**. On the Iceberg documentation that means every search includes
"iceberg table format". The page's own subject therefore matches every
selection made anywhere on it. The scoring then confirmed it, because the
score measured overlap with the page topic — the very thing that was
contaminating the query.

```oku-diagram
{"src":"flowchart TB\n    SEL[\"Selection: Schema\"] --> BIAS[\"Search: 'Schema' + page topic\"]\n    TOPIC[\"Page topic: iceberg, table, format\"] --> BIAS\n    BIAS --> CAND[\"Candidates\"]\n    subgraph BEFORE [\"Before — one score doing two jobs\"]\n      CAND --> SCORE[\"Score: overlap with page topic\"]\n      SCORE --> OLD[\"Apache Iceberg (the reported defect)\"]\n    end\n    TOPIC --> SCORE\n    subgraph AFTER [\"After — gate first, then rank\"]\n      CAND --> GATE{\"About the selection?\"}\n      GATE -->|no| DROP[\"Dropped\"]\n      GATE -->|yes| RANK[\"Then rank by page topic\"]\n      RANK --> NEW[\"Nothing here, so the page's own sentence answers\"]\n    end","caption":"The page topic was feeding both the query and the score, so the page's own subject won every comparison. The gate breaks that loop: relevance to the page can rank candidates against each other, but it can never establish that one answers the question asked."}
```

Three guards now sit at three different causes, which is deliberate — one
guard covering all three would have been a heuristic rather than a fix.

```oku-step-flow
{"ordered":false,"steps":[{"t":"Aboutness gate","b":"A search result must name the selection in its title, or in the lead sentence before its verb. Wikipedia's house style puts the subject there. Deliberately not the rest of the extract — the Iceberg article's second sentence mentions schema evolution, which would let your exact case straight back through."},{"t":"Sentence-start signal","b":"A capital on the first word of a sentence is grammar. It now reaches the router, and a single capitalised token at a sentence start leads with the word reading while still fetching the entity path, so a real name at a paragraph start is not lost."},{"t":"Disambiguation stop","b":"A disambiguation page is Wikipedia stating that the term names several unrelated things. Searching afterwards does not resolve that — it hides it behind whichever article ranked first. The provider now stops and lets the page's own sentence and the dictionary answer."}]}
```

```oku-insight
{"b":"Relevance to the page can rank candidates against each other. It can never establish that one of them answers the question that was asked. Those are different jobs and the code was using one score for both."}
```

## Turkish: the limit you feared is not the one that binds {#turkish}

You said MyMemory might not survive heavy use. That is true of MyMemory and
almost irrelevant to you, because MyMemory should rarely be reached.

Two things were measured today rather than assumed. The dictionary already
returns Turkish head-words per sense — `partition` gives `bölme` straight
from Wiktionary data, no translator involved. And the browser's own
on-device translator produced Turkish in the browser check: the settings page
reported *"English to Turkish is ready and runs on this device"*, and the
card rendered the translation slot.

```oku-table
{"headers":["Path","Daily allowance","What it covers","Status"],"rows":[["Dictionary head-words (Wiktionary)","Unbounded","Single words that Wiktionary has a Turkish entry for","Working now — `partition` → `bölme`"],["On-device translator (browser)","Unbounded, offline, private","Anything: definitions, sentences, technical phrases","Working in Chromium. Needs the language pack downloaded once, from extension settings"],["MyMemory, anonymous","5,000 characters","Fallback only, when the browser has no model","Verified at mymemory.translated.net/doc/usagelimits.php"],["MyMemory, with contact address","50,000 characters, 500 per query","Same","Verified, same page"]]}
```

So the order of operations is already right: on-device first, online only when
the browser has nothing. The work left is not a better online service — it is
making the on-device path easy to turn on and obvious when it is off.

> [!IMPORTANT]
> This is the outstanding item that needs your machine, not mine. Launch
> Brave with `open -a "Brave Browser" --args --enable-features=TranslationAPI`,
> load `dist/chromium` unpacked, open extension settings and press Download.
> Chrome 151 needs no switch at all. Until you see that work in your daily
> browser, nothing further should be built on the on-device path.

If it turns out Brave will not cooperate, the honest fallbacks in order are:
run the extension in Chrome for lookups; or add DeepL as an alternative online
provider. DeepL does publish a free API plan with its own `api-free.deepl.com`
endpoint — **but I could not verify the character allowance**, because the
pricing page renders client-side and returned nothing readable. Treat any
figure you have seen quoted for it as unconfirmed until someone opens the
page.

The honest summary: nothing out there does what you are describing — a single
gesture that answers correctly for an English word, a Turkish translation, a
person, *and* an Iceberg configuration flag. The pop-up dictionaries are
excellent and monolingual-by-domain. The translators translate. Nobody routes
by intent. That is the actual differentiator, and it is also the hardest part
to get right, which is what the relevance section was about.

### Multiple meanings, reachable in one click {#meanings}

The card already shows up to six senses and then silently stops. Two changes,
both small: say how many were dropped, and make each sense clickable to the
source that supplied it. Every sense already carries a `source` field, so the
link target exists — it is simply never rendered.

The design decision worth making now: **a sense links to its own source, not
to a generic search.** A Wiktionary sense opens that Wiktionary entry; a
Stack Exchange answer opens that answer. Anything else is a search box with
extra steps.

### Visual signals instead of more text {#visual}

You described the target well: dense but not complicated. Three mechanisms,
in order of how much they buy per unit of clutter.


The constraint to hold: colour must carry meaning, never decoration. The
moment two things share a colour for different reasons, the whole system
stops being readable and becomes noise with a palette.

### Drag, detach, pin {#pin}

This is a bigger change than it looks, and worth doing properly rather than
cheaply. Dragging by the header is easy. The consequence is not: once a card
is detached it is no longer anchored to a selection, so the placement logic
fixed today must learn a second mode, and a detached card must survive the
next lookup instead of being replaced.

```oku-info-tip
{"summary":"Why this needs a state machine, not a drag handler","content":["The card currently has one lifetime rule: a new lookup replaces it. Detaching introduces a second kind of card that outlives its lookup, and every existing behaviour has to be re-decided against it.",{"k":"code","src":"anchored   -> dragged     : reader moves it\ndragged    -> pinned      : release; keeps its own request id\npinned     -> pinned      : a new lookup opens a SECOND card\npinned     -> closed      : only its own close button\nanchored   -> replaced    : a new lookup reuses it (today's rule)","lang":"text"},"Scroll is the awkward one. An anchored card closes on scroll because its selection has moved away. A pinned card must not — it is no longer about that selection. Same for Escape: it should close the newest, not all of them."]}
```

### The sentence you found it in {#sentence}

Not on your list, but it is the cheapest high-value item here and it makes
three other things better. The page context already captures the enclosing
sentence — it is used to rank senses and, since today, to detect a sentence
start. It is never shown and never exported.

Showing it costs almost nothing. Putting it in the Anki export turns a
vocabulary card into a usable one, which is the Reverso and Yomitan insight
in a single field.

## The local model: your machine is not the blocker {#local-model}

The Prompt API measured `unavailable` on every browser here, and the natural
conclusion was that the machine could not run it. That conclusion is wrong.

```oku-chart-grid
{"title":"Chrome's published Prompt API requirements against this machine","cols":3,"child_type":"bar","panels":[{"title":"Free disk (GB)","rows":[{"label":"required","value":22},{"label":"available","value":1229}]},{"title":"RAM (GB)","rows":[{"label":"required","value":16},{"label":"available","value":64}]},{"title":"CPU cores","rows":[{"label":"required","value":4},{"label":"available","value":10}]}]}
```

Chrome documents 22 GB free disk, 16 GB RAM and 4 cores, on macOS 13 or
later. This machine has 1.2 TB free, 64 GB of RAM, 10 cores, and macOS 15.7.
The Prompt API for extensions shipped in **Chrome 138**, so no origin trial
registration is needed either.

```oku-insight
{"b":"`unavailable` was reporting a switched-off feature, not an incapable machine. In Brave these APIs ship off; in Chrome the model downloads on first use behind a flag. That is a five-minute check, not a hardware purchase."}
```

Two cautions before building anything on it. First, from Chrome 149 the
built-in models support English, Spanish, Japanese, German and French for
input and output — **Turkish is not on that list**, so the local model is a
candidate for ranking and disambiguating English senses, and not for
generating Turkish. Second, the existing `chooseOption()` in
`src/platform/ai.ts` still has no caller. It should get one here or be
deleted; leaving a complete, tested, unreachable function in the tree is how
a codebase starts lying about what it does.

## Can this earn anything, or open doors {#monetise}

Two different questions with two different answers, and conflating them is
how side projects die.

**Direct revenue: possible, small, and probably not worth your time.** Google
shut down Chrome Web Store payments on 1 February 2021, so every paid
extension now carries its own billing — Stripe, Paddle, Lemon Squeezy or
ExtensionPay — plus licence checks, tax handling and support email. That is a
product, not a feature.

```oku-table
{"headers":["Model","How it works here","Honest assessment"],"rows":[["**Free, open source**","Ship it, MIT licence, GitHub Sponsors link.","Fits the architecture exactly. No account, no key, no server is already the promise; charging would require breaking it or building the thing you deliberately avoided."],["**Freemium licence key**","Free core, paid extras: source packs, sync, side panel.","Technically fine via ExtensionPay. But the paid surface would have to be the parts you built for yourself, and you would inherit support duty for them."],["**Paid, one-off**","A licence key unlocks everything.","Lowest support burden of the paid options. Also the hardest sale against Google Dictionary, which is free and adequate for most people."],["**Sponsored or affiliate**","Referral links to dictionaries or courses.","Would contradict the privacy position outright. Not recommended."],["**Bandwidth sharing**","Some extensions monetise by reselling users' bandwidth.","Actively harmful to trust. Do not."]]}
```

**Presence and opportunity: this is the real return, and it is already
earned.** What you have is not a dictionary extension. It is a working
demonstration of intent routing, provider composition with independent
failure modes, on-device inference with graceful absence, and a relevance
problem diagnosed down to a specific mechanism — the subject of the second
section above. That last one is a genuinely good engineering story, and there
is very little written about the Chrome built-in AI APIs from someone who has
actually measured them.

## What I need from you {#decisions}

Four decisions, in the order they block things.

One thing I did not do, and should flag: the relevance changes are pinned by
unit tests built from your two reported cases, but I have not run them against
live Wikipedia for a broad set of terms. The unit tests prove the mechanism;
they do not prove the new behaviour is better across the range of words you
actually select. A short live sweep over twenty real terms would settle that,
and it is worth doing before we build anything further on top of the
relevance layer.
