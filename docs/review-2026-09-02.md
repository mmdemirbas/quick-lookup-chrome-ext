> [!TLDR]
> Round one asked whether the feature was correct. Round two asked whether it
> is still correct on the tenth question, the hundredth token, and the day
> after an upgrade — and then asked the same of the suite that checks it.
>
> - **Seven defects in the feature.** Every one of them is about duration:
>   a thread that grows without a ceiling, a stream that stops early, a
>   thread saved by yesterday's build, a process that never returns.
> - **Six defects in the browser suite**, in two shapes: it could not tell
>   *did not run* from *failed*, and it sampled states that only exist for a
>   moment. One of its polls never polled.
> - **The suite's own flake had a measurable cause**, and following it further
>   found a product defect: on a first run after install, the lookup message
>   sat for fifteen seconds before the worker received it, or never arrived.
>   The page now draws what it can answer itself before the worker is asked.

## What did the first review not look at? {#axes}

Round one drove the feature by hand and found six defects in the states nobody
drives — Stop, Clear, reopen, and a hostile page. It answered one question
well: *is this correct right now?*

Everything below comes from asking six different ones. They are listed here
rather than discovered in the prose because the choice of axis is what decided
the findings, and a reader should be able to see the axis before the result.

```oku-table
{"headers":["Aspect","The question it asks","Defects it found"],"rows":[["Duration","What does the tenth question cost, given the first nine?","1"],["Interruption","What does a half-arrived answer look like?","1"],["Upgrade","What happens to a thread the previous build saved?","1"],["Cost per token","What does drawing one token cost when the thread is long?","1"],["Resource ceilings","What is the most this can be made to consume?","2"],["Reach","Who cannot use this at all?","1"],["The harness","Can the suite tell a broken extension from a quiet network?","6"]]}
```

The last row is the one that changes how the rest should be read. A suite that
cannot fail honestly is not evidence about the six rows above it, and three of
its six defects were in code added during round one.

## What grows without a ceiling? {#growth}

The conversation carries the page you were reading. It carried **every** page
you had read: each attachment was re-sent, in full, on every later turn.

The case the feature exists for makes this arrive quickly. Read a post, open
the paper it cites, ask whether the paper supports the post — that is three
pages before anything unusual has happened.

```oku-chart
{"type":"bar","title":"Pages whose full text travels on request N","rows":[{"label":"Request 3 — before","value":3,"display":"3"},{"label":"Request 3 — after","value":3,"display":"3"},{"label":"Request 10 — before","value":10,"display":"10"},{"label":"Request 10 — after","value":3,"display":"3 (capped)"}]}
```

The chart counts pages, not tokens, because pages are what the code decides
and tokens are what a particular page happens to weigh. The one token figure
worth quoting is the measured one: a ten-page thread built a request of
roughly **67,000 tokens**, and nothing in the code stopped that number
growing.

The fix keeps the newest three in full. Older ones are not removed from the
conversation — they keep their title and URL, so *"the paper you showed me
earlier"* still refers to something. What matters more is that the model is
**told** the text is gone:

```oku-annotated-code
{"src":"<page url=\"https://example.com/3\" title=\"The paper\" text-dropped=\"true\">   // (1)\n[Discussed earlier in this conversation. Its text is no longer included —\nsay so rather than guessing if a question depends on it.]                 // (2)\n</page>","lang":"html","annotations":[{"id":1,"content":"The page is still in the conversation and still has a name. A question about it resolves to <i>something</i>."},{"id":2,"content":"Silently omitting the text is the failure mode this avoids. A model that is not told the page is gone answers from whatever it can still infer, and that answer is indistinguishable from one grounded in the page."}]}
```

Trimming moved one other thing that would have been easy to miss: the prompt
cache breakpoint. It sits on the newest attachment, and a test now pins it
there, because a breakpoint left on a block that no longer travels is a cache
that never reads.

## What does a half-arrived answer look like? {#truncation}

It looked exactly like a whole one.

A stream can stop without saying it is done — a dropped connection, a proxy
closing early, a frame that will not parse. The text collected up to that
point was written into the thread and drawn like any other answer, so an
answer that ended mid-sentence read as an answer that had finished with a
short one.

```oku-compare-grid
{"cards":[{"t":"Before","b":"The turn is stored and drawn identically whether or not `message_stop` ever arrived. A fragment is indistinguishable from a finished answer, including after a reload.","accent":"warn"},{"t":"After","b":"`ChatResult.complete` travels to the panel, the turn carries `truncated`, and the turn is drawn with a **Cut off** label whose tooltip says what is here is a fragment. It is still kept and still replayable.","accent":"success","verdict":"good"}]}
```

Unparseable frames count toward the same verdict: any dropped frame at all
means text is missing, so `complete` is false even when `message_stop` did
arrive.

## What happens to a thread saved by yesterday's build? {#upgrade}

Round one moved `usage` and `backend` inside `Conversation` — the fix that
gave spend and backend a single owner. That was right, and it changed the
shape of what gets written to session storage.

A thread written by the *previous* build has no `usage`. Reading
`usage.inputTokens` off it threw. The throw landed in a `try` that existed for
a different reason — session storage being unavailable — and the handler for
that case starts an empty thread. So the conversation was replaced, silently,
and the panel looked like it had simply been cleared.

```mermaid
flowchart TB
  R["storage.session.get()"] --> P{"parse the stored thread"}
  P -- "throws on the old shape" --> C["catch: storage unavailable"]
  C --> E["start an empty thread"]
  E --> S["the reader sees a cleared panel<br/>and is told nothing"]
  classDef bad fill:var(--series-4-soft),stroke:var(--series-4),color:var(--text)
  class C,E,S bad
```

Two changes, and the second is the one that generalises. The read and the
revive now sit in separate statements, so the catch covers only the read. And
`reviveConversation` validates instead of casting: a turn without a known role
is dropped, a half-written attachment is dropped, a spend total that is not a
number reads as zero rather than becoming `NaN` in the meter.

The general shape is worth naming, because it is not specific to storage: **a
`try` block that covers more than the failure its `catch` describes will one
day swallow something else.**

## What does drawing one token cost? {#render}

Every delta redrew the whole thread.

```oku-chart
{"type":"bar","title":"Milliseconds to draw 300 deltas","rows":[{"label":"Into an empty thread — before","value":103,"display":"103 ms"},{"label":"Into a sixty-turn thread — before","value":450,"display":"450 ms"},{"label":"Either, after","value":0,"display":"one turn replaced"}]}
```

The absolute numbers are small. The direction is the finding: the cost of a
token scaled with how long the conversation already was, which is backwards
for something that only ever appends to the end. The panel now holds the
element the streaming turn is drawn into and replaces that one.

## What is the most this can be made to consume? {#ceilings}

Two ceilings were missing from the local bridge, and neither is about a
stranger — the token already keeps strangers out. They are about a bug, or
several panel windows, or a `claude` process that simply never returns.

```oku-table
{"headers":["Missing ceiling","What it allowed","Now"],"rows":[["No answer timeout","A wedged child holds a subscription slot and a pipe for as long as the client stays connected — for a side panel left open, indefinitely","Killed at 180 s, with a message that says it was a timeout rather than an exit code"],["No concurrency cap","Nothing bounded how many `claude` processes this machine would be running","`429` above four in flight, naming the count"]]}
```

The timeout message is deliberately not the generic one. *"Claude Code exited
with code null"* sends a reader to look for a crash; *"did not answer within
180 seconds and was stopped"* sends them to look at the question.

## Who cannot use this at all? {#reach}

Someone listening to it. The panel had a tab switcher that was two buttons,
turns that were two runs of prose, and no announcement of anything.

- The tablist has `role="tab"` / `role="tabpanel"` with `aria-controls` and
  `aria-labelledby`, a roving tabindex so the pair is one tab stop, and
  arrow / Home / End keys — which is the half of the pattern a native button
  stops giving you for free once the tabindex roves.
- Each turn carries `aria-label="Your question"` or `"Answer"`. Without it a
  listener hears two runs of prose and nothing says which was which.
- A visually-hidden `role="status"` region announces the transitions —
  *Answering.* / *Answer finished.* / *The answer was cut off before it
  finished.*

The status region is deliberately **not** a live region on the log. A live
log re-announces the whole answer on every token, which is worse than silence.
What a listener needs is the transitions, and then the ability to go and read
it.

## Can the suite tell a broken extension from a quiet network? {#harness}

Not until this round, and three of the four defects were in code round one had
added for exactly that purpose. This is the part of the review most worth
reading, because a check that reports the wrong thing is more expensive than
no check.

### The poll that never polled {#poll}

Round one added a poll so the in-context sentence and its mark were read
together rather than across a re-render. It went red anyway, roughly one run
in two, reporting `mark=""`.

```oku-annotated-code
{"src":"// Before\nconst read = async (selector) =>\n  (await page.locator(selector).first().textContent().catch(() => null)) ?? '';  // (1)\n\nfor (;;) {\n  const last = { marked: await read('… .incontext mark'), … };\n  if (good || Date.now() > until) return last;                                  // (2)\n  await page.waitForTimeout(150);\n}\n\n// After\n  (await page.locator(selector).first().textContent({ timeout: 400 })            // (3)\n    .catch(() => null)) ?? '';","lang":"javascript","annotations":[{"id":1,"content":"No timeout, so a miss waits Playwright's default: <b>30 seconds</b>."},{"id":2,"content":"The deadline is 8 seconds. The first miss outlives it, so the loop returns one stale sample and never iterates. The failure message printed <code>mark=\"\"</code> for a card whose DOM, read in the same iteration, contained <code>A &lt;mark&gt;manifest&lt;/mark&gt; is a metadata file…</code> — which is what gave it away."},{"id":3,"content":"Bounding the read is what makes it a poll. Without this the loop is a 30-second sleep wearing a loop's shape."}]}
```

### The gate that counted the wrong sources {#gate}

Round one added `E2E_OFFLINE=1` so the outage branch could be exercised on
purpose instead of only when the network happened to be down. It did not work,
and the reason is one line: *online* was defined as **any** source answering.

The page itself is a source. It always answers on the fixture. So with every
external host blocked, `online` was still true, the skip gates never fired,
and a blocked network produced three failures.

`online` now means *a source that had to leave the machine answered*, with the
local labels imported from the providers rather than spelled out, so renaming
one cannot quietly re-break it.

### Forgiveness that only caught half the failures {#forgive}

The wrapper that turns "could not run" into a skip caught **thrown** timeouts.
Several checks never throw one: they write `.waitFor(…).catch(() => false)`
and record a plain failure, which no `catch` around the group can see.

```mermaid
flowchart LR
  T["a wait times out"] --> K{"how was it written?"}
  K -- "left to throw" --> A["caught by the group<br/>→ skipped"]
  K -- "`.catch(() =&gt; false)`" --> B["recorded as a failure<br/>→ red, and invisible to the catch"]
  B --> F["now: failures recorded inside an<br/>offline group become skips too"]
  classDef bad fill:var(--series-4-soft),stroke:var(--series-4),color:var(--text)
  classDef good fill:var(--series-2-soft),stroke:var(--series-2),color:var(--text)
  class B bad
  class A,F good
```

### Two checks that watched a state lasting a moment {#transient}

The other shape, found by running the suite on a machine that was busy. Both
of these had been green for weeks and both report the extension as broken.

- **Stopping "before a single word arrives".** The stub emits a word every
  300 ms, and the check sends, waits for the button to read *Stop*, and
  presses it. Under load that round trip outran 300 ms, a word arrived, and
  the turn kept the text — which is the behaviour the feature is supposed to
  have. The premise was made true by construction instead: a marker in the
  question holds the stub's first frame for five seconds.
- **"The copy button says so".** The button reads *Copied* for 1.4 seconds
  and then puts its name back. The check clicked, read the clipboard, then
  went to look at the button — two round trips, which on a loaded machine
  outlived the label. Giving the look a deadline does not fix this, because
  what starts late is the looking. The transition is now **recorded** by a
  mutation observer installed before the click, which cannot miss it, and it
  keeps the original claim by remembering the most buttons that ever said so
  at once.

The general form is worth keeping: **a check that samples a state which
exists only briefly is testing the machine's spare capacity.** Either hold
the state still, or record the transition rather than looking for it.

### Assertions that raced a cold start {#coldstart}

The remaining flake had a cause that could be measured rather than guessed.
Repeating only the first selection, on a fresh profile:

```oku-table
{"headers":["What was measured","Result"],"rows":[["Double-click to the first filled slot, machine otherwise idle","≈ 1 s, in each of three runs — the sampler reads once a second, so this is an upper bound"],["The same, while three browser runs competed for the machine","≈ 4 s"],["One lookup per fresh page sampled at 2.5 s, under that same load","5 consecutive cards with no slots and no sources at all"],["The same, machine idle","Filled by the first sample, every time"],["Those empty cards, watched to 40 s","Filled — late, not lost"]]}
```

The load dependence is why this read as a network problem for so long: on a
quiet machine the suite passes, and it goes red when something else is
running. The suite asserted on slots immediately, with a fixed 2.5 s sleep
sitting further down doing the settling job for the checks *after* it. Under
load the cold start exceeded both.

The script that produced these numbers is committed as
[tools/cold-start.mjs](#f/tools/cold-start.mjs), in both modes, so the next
person to meet this flake re-measures with one command rather than
re-deriving the method.

The card already says when it is done: a slot still waiting draws a `.pending`
skeleton, and the composer clears the last of them only once every provider
has settled. The suite now waits for that, and the sleep is gone.

> [!NOTE]
> Waiting for the *first* source was tried first and is wrong for a reason
> worth recording: the local page answers before any network source, so the
> wait ended early and the run then reported itself offline — turning a
> healthy network into three silent skips. Right signal, wrong threshold.

## Where do fifteen seconds go on a first run? {#firstrun}

The cold-start numbers above were enough to fix the suite. They were not an
explanation, and the spread — one second, four, eleven — said the cause had
not been found. So the lookup path was instrumented end to end and the first
selection repeated on a fresh profile.

```oku-table
{"headers":["Step","Time after the double-click, run 2","Run 3"],"rows":[["Content script sends the lookup message","251 ms","252 ms"],["Worker receives it","15,023 ms","16,121 ms"],["Settings read","+9 ms","+13 ms"],["Pack signature read","+22 ms","+12 ms"],["Cache read","+0 ms","+0 ms"],["First card emitted","+1 ms","+1 ms"],["Page provider's slot emitted","+6 ms","+2 ms"]]}
```

Run 1 never delivered the message inside the 20-second cap. Once the worker
has the message, the whole lookup path is under fifty milliseconds; every
await it does — settings, pack signature, cache — measured in the tens of
milliseconds even on a cold profile. The time is spent **before** the
message arrives, inside the browser, and the promise the content script is
holding does not reject while it waits. The comment at that call site said the
message had been *dropped* and nothing could be shown. It is not dropped; it
is late, and something could be shown.

Two more measurements bound the finding. Stopping the worker over the
DevTools protocol — the state Chrome puts it in after thirty seconds idle —
and looking up again cost **348 ms** to the page's own answer, the same as a
warm worker (`wake` mode of [tools/cold-start.mjs](#f/tools/cold-start.mjs)). The delay belongs to the first run after install, not to every
lookup after a pause. And this could not have been seen with Playwright's
own idle: the attached session keeps the worker alive, which is why a
45-second wait earlier in the session showed nothing.

```mermaid
flowchart LR
  S["selection"] --> C["content script<br/>has the page's sentence<br/>and definitions already"]
  C -- "before" --> W["message to the worker<br/>15 s on a first run"]
  W --> D["card drawn"]
  C -- "after" --> L["local card drawn<br/>page + links, rest pending"]
  L --> W2["message to the worker"]
  W2 --> R["worker's card replaces it<br/>as each provider lands"]
  classDef bad fill:var(--series-4-soft),stroke:var(--series-4),color:var(--text)
  classDef good fill:var(--series-2-soft),stroke:var(--series-2),color:var(--text)
  class W bad
  class L,R good
```

The fix is the thing the earlier open item asked about. The two providers
that need nothing but the page — the page itself and the quick links — are
run by the content script and drawn before the worker is messaged. Three
rules keep that honest:

- **A card never goes backwards within one lookup.** The worker's first emit
  is empty and arrives after the local card; drawing it would blank the
  sentence for a few milliseconds. Sources only accumulate, so a card with
  fewer of them is older and is ignored.
- **A worker that never answers does not leave skeletons up for good.** After
  the worker's own budget plus three seconds, the local card is settled in
  place — the pending slots marked unavailable — unless a worker card has
  arrived for that request.
- **The local card is the same with or without a network.** It runs no
  provider that could fetch, and a unit test pins that.

Measured after, on a fresh profile, three runs (`first` mode of the same
script): the page's own answer drawn at **775, 863 and 1,290 ms** after the
double-click, most of which is the selection dwell. The suite reads the card at first paint and asserts the
page's answer is already in it.

This is not free. The content script is injected into every page, and running
the intent router there to get the slot order right from the first paint is
what it costs:

```oku-chart
{"type":"bar","title":"Content script, gzipped","rows":[{"label":"Before","value":17578,"display":"17.6 kB"},{"label":"After","value":22231,"display":"22.2 kB  (+26%)"}]}
```

The growth is the intent router and its signals, the card layout, and the two
local providers — measured module by module, with nothing unexpected in it.
The alternative was a fixed local layout, about 3 kB cheaper, at the price of
the card visibly reshuffling when the worker's intent disagreed. The order the
reader sees first should be the order they keep.

What is *not* established is why the browser holds the message for fifteen
seconds on a first run. The extension's own install handler creates three
context-menu items and prunes the cache, none of which takes seconds. The
number was reproduced, not explained, and the fix does not depend on the
explanation.

## Verification {#verification}

```oku-table
{"headers":["Gate","Result","What it covers"],"rows":[["`npm run check`","Typecheck clean, 269 unit tests pass, build succeeds","Page trimming and its cache breakpoint, the revive path and its four rejection cases, the cost arithmetic, the local card running no provider that could fetch"],["`npm run e2e`","Green, twice in a row","The whole extension in a real browser, including settle-before-assert and the page's answer being in the card at first paint"],["`E2E_OFFLINE=1 npm run e2e`","Green, with the network-dependent checks reported as skipped","The outage branch, now made at the resolver so nothing escapes it"],["`node tools/cold-start.mjs first`","Page's answer at 775–1,290 ms on a fresh profile, three runs","The first lookup after install, which used to wait on the worker for fifteen seconds or longer"],["Content script size, built from `HEAD` and from this branch","17.6 kB → 22.2 kB gzipped","What the local card costs every page the extension is injected into"]]}
```

Round one's closing note said the stub that made Stop testable was the part
most likely to pay again. It did, immediately: the `E2E_OFFLINE` flag and the
settle-before-assert wait are the same idea applied to the other half — the
suite can now be put into the state it fails in, instead of waiting for that
state to happen when nobody is watching.
